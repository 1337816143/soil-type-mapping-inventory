## 配置与安全部署

目标流程是：使用者输入管理密码 → 后台授权 → 后台调用 GitHub。**不是隐藏前端输入框，或继续把明文 Token 放进会发送到浏览器的脚本。**

一次性维护端配置：

| 名称 | 放置位置与用途 |
|---|---|
| `CLOUDFLARE_API_TOKEN` | 维护者本机/受保护CI环境：部署 Worker 的授权，不放浏览器 |
| `CLOUDFLARE_ACCOUNT_ID` | 维护端：确认属于本人的 Cloudflare 账户 |
| `GITHUB_UPLOAD_TOKEN` | Worker Secret：仅授权当前仓库，至少 Contents Read/Write；实际暂存工作流触发须再验收 |
| `SOIL_ADMIN_PASSWORD` | Worker Secret：平台管理员密码，由维护者设置，不提交代码 |
| `SESSION_SECRET` | Worker Secret：至少32字符随机值；部署脚本未提供时自动生成 |

不要把以上敏感值发到聊天、写入公开仓库，或填入当前网站的 PAT 弹窗。Cloudflare 的 Worker Secret 通过部署工具安全上传；不是仓库文件。已有公开前端凭证不应被当成秘密继续使用；迁移完成后的旧凭证撤销和管理密码调整须由维护者确认，本候选不会自动执行。

维护者在本机安全设置前4项环境变量后，可以执行：

```bash
node backend-v2/scripts/build-directory.cjs .
node backend-v2/scripts/deploy-candidate.mjs
```

脚本只部署**新名称** `soil-managed-upload-v2` 的后台，不改前台，不撤销旧凭证；配置文件 `WRITES_ENABLED=false`，部署后默认只允许健康与鉴权检查。真实写入验收必须由维护者明确开启，完成唯一标记测试文件的上传、展示、下载及删除后再接前台。不要运行仓库中的旧 `Deploy upload Worker` 流程来替代：它会整体重写现有上传配置。

## API

所有 `/v1/*` 请求要求允许的 Origin；管理接口还要求 `/v1/login` 取得的短期 Bearer 会话。CORS 不是权限校验的替代。每个登录来源15分钟最多10次尝试，任务会话保留30分钟，上传状态保留48小时。

| 路径 | 用途 |
|---|---|
| `GET /health` | 配置与只读模式状态，不返回密钥 |
| `POST /v1/login` | `{"password":"由使用者输入"}`，失败不访问GitHub |
| `POST /v1/logout` | 撤销当前短期会话 |
| `GET /v1/readiness` | 后台真实读取目标仓库状态，不产生写入 |
| `POST /v1/uploads` | 创建质控/参考任务；要求唯一 Idempotency-Key |
| `PUT /v1/uploads/{id}/files/{index}/parts/{part}` | 接收该任务已声明的二进制分块 |
| `POST /v1/uploads/{id}/finalize` | 接入原归档工作流；重复调用不重复建分支 |
| `GET /v1/uploads/{id}` | 区分接收中、归档中、已归档；不因轮询断网要求重传 |
| `POST /v1/delete-plans` | 生成只含允许路径的删除确认计划 |
| `POST /v1/delete-plans/{id}/confirm` | 明确确认，仓库版本变化则中止 |

后台不提供任意 GitHub URL/方法/分支代理，也不接受客户端指定凭证、仓库、目标分支或索引路径。管理删除中索引异常、仓库树被截断时拒绝操作，不按空索引继续。

候选传输每段8 MiB，仍支持单文件95 MiB；原文件并不被拆成多个成果文件。一次请求批次最多30文件/512 MiB，单文件最多100条关联，元数据体有界。前台正式接入时需将更大批量自动分批，不能直接减少用户原有批量上传能力。
